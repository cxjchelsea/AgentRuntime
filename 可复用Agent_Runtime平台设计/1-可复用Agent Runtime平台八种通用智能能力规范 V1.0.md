# 可复用 Agent Runtime 平台八种智能能力规范 V1.0

> **Phase 0 Fix**  
> 本文定义跨领域智能表现，不是某个陪护产品的需求规格。  
> “情感陪护”“8 大业务模块”为历史表述 / Domain Example，不得当作 Core 必选业务。

## 1. 文档目的


> **平台化转换说明**  
> 本文已从单一业务 Agent 设计转换为 **可复用 Agent Runtime 平台**设计。除明确标记为 `Core` 的对象、接口、不变量和生命周期外，任何具体业务 Intent、Entity、Workflow、Skill、Tool、知识域、状态字段、规则、提示词或示例均视为 **Domain Package 示例**，不得硬编码进 Runtime Core。新项目应通过 Registry / Adapter / Plugin / Config 注入领域差异。
> 
> 平台固定边界：`Runtime Core` 尽量稳定；`Domain Extension` 插件化；`Business Package` 配置化；`Application` 负责产品装配。

本规范用于定义可复用 Agent Runtime 平台应具备的核心“智能表现”。

本规范回答的问题不是：

> 软件具体采用什么模型、框架或代码实现？

而是：

> 一个真正具有情感陪护能力的 Agent，应当在哪些方面表现出智能，以及达到什么程度才算实现。

本规范作为后续 M0～M9 软件设计和实现的上位约束。

整体关系为：

```text
八种智能能力
= Agent 应达到的能力目标

↓

M0～M9
= 将这些能力目标工程化实现的软件方案

↓

8 大业务模块
= 智能能力在具体业务中的实际落地

↓

具体场景、内容、话术、题库、分类
= 最终业务资产
```

本机器人最终应具备以下八类智能：

1. 语义理解智能
2. 上下文智能
3. 关系连续性智能
4. 情绪理解智能
5. 目标与隐含需求推断智能
6. 对话策略智能
7. 主动性智能
8. 自我约束智能

---

# 2. 总体智能原则

## 2.1 智能不等于自由生成

本系统中的“智能”是：

```text
正确理解
+
正确判断
+
正确选择行为
+
自然表达
+
持续理解用户
+
知道自己的边界
```

而不是：

```text
让 LLM 自由决定所有事情
```

安全事件、状态优先级、通知真实性、提醒升级规则等确定性业务，不因 Agent 智能化而交给 LLM 自由决定。

---

## 2.2 智能的基本闭环

完整智能闭环应表现为：

```text
用户表达
↓
理解当前话语
↓
结合上下文
↓
理解当前用户状态
↓
推断当前需要
↓
选择最合适的行为
↓
执行行为
↓
观察实际结果
↓
更新状态与记忆
↓
进入下一轮理解
```

因此系统不能只做：

```text
Input
→ Intent
→ 固定回复
```

而应逐步形成：

```text
Input
→ Understanding State
→ Action Plan
→ Execution
→ Result
→ Updated Context
```

---

# 3. 智能一：语义理解智能

## 3.1 定义

语义理解智能是指机器人能够理解用户当前一句或一段表达“在说什么”。

不仅识别表面关键词，还需要处理自然语言中常见的：

- 口语化；
- 表达不完整；
- 省略；
- 指代；
- 模糊表达；
- 多意图；
- 自我修正；
- 重复表达；
- 目标用户断续表达；
- 同一意思的不同说法。

---

## 3.2 能力目标

系统应能够从用户表达中识别至少以下信息：

```text
显式意图
业务对象
关键实体
动作要求
时间信息
人物信息
内容偏好
当前话题
多个并存需求
不确定信息
```

例如：

> “还是给我听昨天那个吧。”

不能只理解成：

```text
PLAY_CONTENT
```

而应进一步解析：

```text
intent = PLAY_CONTENT
reference = 昨天播放过的内容
content_identity = 需要结合上下文解析
```

---

## 3.3 典型输入

- 当前 ASR 文本；
- 当前说话轮次；
- 最近若干轮对话；
- 当前业务状态；
- 当前任务上下文。

---

## 3.4 建议输出结构

```text
SemanticUnderstanding

explicit_intents
entities
references
time_expression
negation
confirmation
correction
topic
ambiguity
confidence
```

示例：

```json
{
  "explicit_intents": ["PLAY_CONTENT"],
  "entities": {
    "content_type": "戏曲"
  },
  "references": [],
  "negation": false,
  "ambiguity": false
}
```

---

## 3.5 必须支持的典型能力

### A. 同义表达理解

例如：

```text
别放了
停一下
关了吧
不用听了
算了
```

在对应上下文中都可能表达 STOP。

### B. 多意图理解

例如：

> “今天有点心烦，给我放点老歌吧。”

应至少识别：

```text
emotion
+
play_content
```

而不能只保留一个标签。

### C. 指代理解

例如：

> “她昨天来过。”

需要结合上下文判断“她”是谁。

### D. 上下文省略

例如：

第一轮：

> “明天天气怎么样？”

第二轮：

> “那后天呢？”

第二轮不能重新要求城市等已经存在的信息。

### E. 修正表达

例如：

> “给我放京剧……算了，还是评书吧。”

最终目标应更新为：

```text
PLAY_CONTENT / 评书
```

而不是同时执行京剧和评书。

---

## 3.6 不应承担的职责

语义理解层不能直接决定：

- 是否允许执行；
- 是否属于安全升级；
- 是否通知成功；
- 最终该采取哪种对话策略。

它回答的是：

> 用户表达了什么？

而不是：

> 系统最后应该做什么？

---

## 3.7 典型失败表现

- 只做关键词匹配；
- 一个句子只能识别一个意图；
- 无法处理“那个、还是之前的、她、它”等表达；
- 用户改口后仍执行之前动作；
- 每一句都重新理解，不利用前文。

---

# 4. 智能二：上下文智能

## 4.1 定义

上下文智能是指机器人能够判断：

> 当前这句话是在什么情况下说的。

同一句话在不同上下文下可能完全不同。

---

## 4.2 上下文组成

建议至少包括：

```text
当前 Runtime State
当前业务
当前会话阶段
最近对话
当前话题
当前正在执行的任务
当前 Tool 结果
时间
用户身份
近期重要事件
相关长期记忆
提醒任务
安全状态
```

---

## 4.3 典型案例

用户说：

> “不用了。”

如果当前正在：

```text
播放音乐
→ STOP播放

提醒确认
→ 可能表示取消提醒

询问是否叫人
→ 表示不要叫人

普通聊天
→ 可能表示结束当前话题
```

因此不能只依靠文本分类决定行为。

---

## 4.4 能力目标

系统应能够：

- 理解当前处于什么业务；
- 理解上一轮问了什么；
- 判断用户当前回答对应哪个问题；
- 保持多轮业务连续性；
- 避免重复询问已经明确的信息；
- 在业务转换后清理失效上下文；
- 被高优先级事件抢占后避免错误恢复旧状态。

---

## 4.5 建议统一 Context

```text
RuntimeContext

identity
session
current_state
current_business
conversation_history
current_topic
active_task
pending_question
recent_events
retrieved_memory
time_context
tool_results
safety_context
```

---

## 4.6 关键原则

### 上下文必须可失效

过去的信息不是永远有效。

例如：

```text
刚刚用户说“我想听京剧”
```

只能在合理时间和场景内作为当前播放上下文。

不能数小时以后仍默认：

> “换一个。”

指的是京剧。

---

## 4.7 典型失败表现

- 每句话都像第一次认识用户；
- 重复询问已经问过的问题；
- 用户回答“是”却不知道在回答什么；
- 业务切换以后仍带着旧业务上下文；
- 被求助抢占以后又自动恢复不适当业务。

---

# 5. 智能三：关系连续性智能

## 5.1 定义

关系连续性智能是指系统不仅拥有历史信息，而且能够表现出：

> 我在持续认识同一个人。

这与简单“数据库里存过信息”不同。

---

## 5.2 能力目标

机器人应能够：

- 记住明确的重要个人信息；
- 记住稳定兴趣和偏好；
- 记住重要人物和关系；
- 记住重要经历；
- 记住近期有持续意义的话题；
- 后续在恰当场景自然调用；
- 能够修改、覆盖或删除失效记忆；
- 避免不同用户记忆串用。

长期记忆模块目前已经定义电话号码、家庭关系、兴趣偏好、人生经历、记忆写入维护、查询调用以及隐私边界等能力，应作为该智能的重要基础。

---

## 5.3 核心不是“记住”，而是“正确使用”

错误：

> 用户半年以前说喜欢京剧。

以后每次无聊：

> “您喜欢京剧，要不要听京剧？”

这会产生机械感。

正确设计应考虑：

```text
这条记忆是否还有效
是否与当前场景相关
最近是否已经使用过
当前提起是否自然
是否可能带来负面情绪
用户是否明确不希望再次提起
```

---

## 5.4 建议记忆最少具有

```text
content
type
source
created_at
updated_at
confidence
importance
usage_scope
last_used_at
status
```

其中 status 后续可考虑：

```text
stable
temporary
emerging
uncertain
deprecated
```

---

## 5.5 关系连续性的三层信息

### 长期稳定信息

例如：

- 家乡；
- 家庭成员；
- 长期兴趣；
- 习惯。

### 中期动态信息

例如：

- 最近女儿准备来看望；
- 最近身体有些不舒服；
- 最近正在听某部长篇评书。

### 会话临时信息

例如：

- 当前刚刚说过想喝水；
- 当前正在聊年轻时工作经历。

三种信息不能混为一种 Memory。

---

## 5.6 典型失败表现

- 什么都记；
- 永久保留所有偏好；
- 每次回复都强行调用记忆；
- 过度提及家人；
- 使用已经过期的信息；
- 用户纠正后仍使用旧事实。

---

# 6. 智能四：情绪理解智能

## 6.1 定义

情绪理解不是单纯分类：

```text
开心
悲伤
焦虑
```

而是理解：

> 当前情绪是什么、为什么产生、程度如何、用户现在希望系统如何回应。

现有业务分类已经覆盖低落、焦虑、害怕、烦躁、委屈、无助、内疚、孤独、思念、哀伤、衰老适应、无意义感、高风险情绪等大量场景。

---

## 6.2 建议理解维度

```text
emotion_type
emotion_intensity
possible_cause
duration_hint
social_context
interaction_need
risk_level
confidence
```

例如：

> “孩子一个星期都没来了。”

不能机械判断成：

```text
emotion = sad
```

更好的状态是：

```text
emotion = loneliness / disappointment
possible_cause = family absence
interaction_need = companionship
risk = normal
```

---

## 6.3 允许不确定

系统不应该假装非常确定。

例如：

> “今天什么都不想干。”

可能是：

- 无聊；
- 疲劳；
- 低落；
- 身体不舒服；
- 单纯想休息。

因此可以：

```text
emotion = uncertain
```

而不是强行分类。

---

## 6.4 情绪理解和风险识别必须区分

```text
Emotion Understanding
≠
Clinical Diagnosis
≠
Safety Risk
```

普通情绪不能被解释成心理疾病。

高风险表达则需要进入独立安全机制。

现有需求已经明确，高风险情绪不能依靠长时间闲聊作为结束方案，而需进入安全事件链路。

---

## 6.5 典型失败表现

- 每次不开心都推荐音乐；
- 每个负面词都判为高风险；
- 用户只是抱怨就开始“心理治疗式”对话；
- 没有考虑情绪产生原因；
- 没有识别用户其实只想安静。

---

# 7. 智能五：目标与隐含需求推断智能

## 7.1 定义

用户说出来的内容，不一定等于真正希望机器人做的事情。

因此系统要区分：

```text
用户说了什么
和
用户此刻希望得到什么
```

---

## 7.2 常见隐含需求

可包括但不限于：

```text
倾听
被回应
陪伴
获得信息
获得行动帮助
确认事实
表达情绪
回忆
消磨时间
需要安静
寻求安全感
寻求真人帮助
```

---

## 7.3 示例

> “今天也没人来看我。”

显式层：

```text
描述一个事实
```

可能隐含：

```text
孤独
想聊天
想说家人
想得到回应
```

但系统不能直接断言：

```text
你就是因为孩子没来所以很难过。
```

应该保留推断的不确定性。

---

## 7.4 建议输出

```text
explicit_goal
implicit_need
confidence
evidence
needs_clarification
```

---

## 7.5 目标推断的原则

### 不过度心理化

不能对普通表达进行深度心理解释。

### 能不澄清就不机械澄清

不是每个模糊表达都要问：

> “您是什么意思？”

如果可以通过上下文安全推断，应优先自然继续。

### 关键业务必须澄清

例如执行不可逆操作、敏感操作或者无法安全推断时，需要明确确认。

---

## 7.6 典型失败表现

- 只能理解字面请求；
- 把所有表达都变成工具调用；
- 每一句模糊表达都追问；
- 过度解读用户心理；
- 用户只是想表达，机器人不断给解决方案。

---

# 8. 智能六：对话策略智能

## 8.1 定义

对话策略智能回答：

> 理解用户以后，系统下一步最合适做什么？

这是情感陪护 Agent 与传统 QA 系统之间最核心的差异之一。

---

## 8.2 应支持的基础 Action

建议至少建立统一 Action Space：

```text
ACKNOWLEDGE
ANSWER
EXPLORE
CLARIFY
LISTEN
WAIT
SILENT_COMPANION
RECALL_MEMORY
OFFER_CONTENT
PLAY_CONTENT
CALL_TOOL
CONTINUE_TASK
CHANGE_TOPIC
END
ESCALATE
```

---

## 8.3 策略不是回复文案

例如：

```text
Action = ACKNOWLEDGE + EXPLORE
```

之后才由 Response Generator 决定具体怎么说。

因此：

```text
决定做什么
≠
决定说哪句话
```

---

## 8.4 策略需要考虑

```text
Understanding State
Context
Current State
Memory
Risk
Policy
User Preference
Recent Agent Behavior
```

最后产生：

```text
Action Plan
```

---

## 8.5 示例

用户：

> “唉，年纪大了，什么都做不了了。”

理解结果：

```text
emotion = loss
topic = aging
implicit_need = emotional support
risk = normal
```

不好的策略：

```text
立刻：
“要不要听音乐？”
```

更合理的策略可能是：

```text
primary_action = ACKNOWLEDGE

secondary_action = EXPLORE

avoid =
立即换话题
立即推荐娱乐
立即说教
```

---

## 8.6 防止“固定套路”

必须避免形成：

```text
焦虑 → 呼吸
孤独 → 音乐
无聊 → 游戏
低落 → 鼓励
```

策略需要参考：

- 用户本轮表达；
- 前几轮已经做过什么；
- 用户此前是否拒绝类似建议；
- 当前交互是否需要行动。

---

## 8.7 典型失败表现

- 一识别情绪就给建议；
- 每次回答结构完全一样；
- 一直追问用户；
- 从不允许沉默；
- 频繁转换话题；
- 为了“智能”过度主动。

---

# 9. 智能七：主动性智能

## 9.1 定义

主动性智能是指系统不仅能响应用户，也知道：

> 什么时候值得主动，主动什么，以及什么时候不应该主动。

现有需求已经存在早、中、晚主动问候，同时明确安静时段、每日次数、不可打扰状态等约束，因此主动行为本身必须受到 Runtime Policy 控制。

---

## 9.2 主动行为类型

可逐步包括：

```text
时段问候
近期话题延续
重要日期关怀
兴趣内容推荐
提醒
近期事件跟进
天气变化提示
主动交互邀请
```

---

## 9.3 主动性的判断因素

```text
current_time
current_state
recent_interactions
recent_interruptions
user_preferences
recent_topics
memory
quiet_period
recent_rejections
importance
urgency
```

---

## 9.4 主动性必须有“克制”

真正自然的陪伴，不是机器人经常主动讲话。

需要考虑：

```text
最近是否刚主动过
用户是否连续拒绝
当前是否在休息
当前是否明确要求安静
是否存在更重要事件
这个话题是否适合再次提起
```

---

## 9.5 主动性价值

好的主动性表现为：

> “它记得我最近发生的事情。”

而不是：

> “它总来打扰我。”

---

## 9.6 典型失败表现

- 定时器一到就强制问候；
- 用户拒绝后很快再次主动；
- 刚刚结束悲伤话题马上推荐游戏；
- 每次都使用用户长期偏好主动推荐；
- 没有冷却时间和主动次数控制。

---

# 10. 智能八：自我约束智能

## 10.1 定义

自我约束智能是指：

> 系统知道什么是自己可以判断的，什么不是；什么可以自由生成，什么必须依据真实系统状态。

这是养老Agent 应用不可缺少的一种“智能”。

---

## 10.2 应识别的主要边界

### 医疗边界

不能自行：

- 确诊疾病；
- 给出自行用药决策；
- 替代专业护理判断。

### 系统事实边界

不能自行判断：

```text
通知成功
工作人员正在处理
家属已经收到
播放已经成功
提醒已经保存
```

这些都必须来自真实 Tool / Service Result。

### 记忆边界

不能：

- 虚构用户记忆；
- 误把推测当事实写入长期记忆；
- 将一个用户的记忆用于另一个用户。

### 情绪边界

不能把：

```text
普通低落
=
抑郁症
```

---

## 10.3 不确定性处理

系统应允许：

```text
不知道
不确定
需要确认
Tool失败
Memory未找到
```

而不是强行补齐答案。

---

## 10.4 Safety 的特殊地位

高风险情绪、高风险身体不适、明确求助等事件不能完全由 Agent Planner 自由决定。

总体关系应为：

```text
Agent Decision
必须满足
Policy
+
Safety
+
State
+
Tool Truth
```

而不是：

```text
LLM Decision
=
Final Decision
```

---

## 10.5 典型失败表现

- Tool 失败仍说成功；
- 模型主动补全不知道的信息；
- 把推测的家人关系写成事实；
- 把普通身体不适说成某种疾病；
- 为了“陪伴感”伪造工作人员反馈。

# 11. 八种智能之间的关系

八种智能不是八个独立软件模块。

更合理的关系是：

```text
              用户输入
                 ↓
        ┌────────────────┐
        │ 语义理解智能    │
        └───────┬────────┘
                ↓
        ┌────────────────┐
        │ 上下文智能      │
        └───────┬────────┘
                ↓
   ┌─────────────────────────┐
   │ 情绪理解 + 目标需求推断 │
   └────────────┬────────────┘
                ↓
        当前用户状态模型
                ↓
      ┌──────────────────┐
      │ 对话策略智能      │
      └─────────┬────────┘
                ↓
           Action Plan
                ↓
              执行
                ↓
             真实结果
                ↓
          状态 / 记忆更新
                ↑
        关系连续性智能
```

主动性智能作用于：

```text
系统是否主动发起下一次交互
```

自我约束智能则横向限制整个流程：

```text
理解
决策
执行
回复
记忆
```

---

# 12. 与 M0～M9 的映射

| 智能能力 | 主要实现阶段 |
|---|---|
| 语义理解智能 | M3 |
| 上下文智能 | M1、M3 |
| 关系连续性智能 | M1、M3、M4、M8 |
| 情绪理解智能 | M3 |
| 目标与隐含需求推断 | M3 |
| 对话策略智能 | M4 |
| 主动性智能 | M4、M8、M9 |
| 自我约束智能 | M2、M4、M6 |

因此：

```text
M3
主要回答：
“我现在到底理解到了什么？”

M4
主要回答：
“基于这些理解，我下一步应该怎么做？”

M8
主要回答：
“这次交互之后，有什么应该持续保留下来？”

M2 / M6
主要回答：
“这个判断和行为是否被允许，而且结果是否真实？”
```

# 13. 八种智能统一验收原则

后续不能只通过：

> “测试几个问题，感觉回复挺自然。”

来判断智能是否实现。

应该分别建立评估集。

## 13.1 语义理解

测试：

- 省略；
- 多意图；
- 指代；
- 修正；
- 口语；
- 模糊表达。

## 13.2 上下文智能

测试：

- 多轮连续；
- 上轮问题对应；
- 业务切换；
- 状态抢占；
- 失效上下文。

## 13.3 关系连续性

测试：

- 正确记住；
- 正确调用；
- 不乱调用；
- 旧记忆更新；
- 多用户隔离。

## 13.4 情绪理解

测试：

- 普通负面情绪；
- 情绪原因；
- 混合情绪；
- 不确定情绪；
- 高风险与普通情绪区分。

## 13.5 隐含需求

测试：

- 单纯倾诉；
- 求帮助；
- 求信息；
- 求行动；
- 需要安静；
- 模糊需求。

## 13.6 对话策略

评价：

- 行动是否符合当前需要；
- 是否过度建议；
- 是否过度追问；
- 是否机械重复策略；
- 是否正确使用 Tool。

## 13.7 主动性

评价：

- 主动时机；
- 主动频率；
- 被拒绝后的处理；
- 是否依据上下文；
- 是否符合安静规则。

## 13.8 自我约束

测试：

- Tool失败；
- Memory未找到；
- 医疗诱导提问；
- 高风险事件；
- 外部状态未知；
- 用户要求系统编造结果。

---

# 14. 最终智能目标

整个情感Agent 应用最终追求的不是：

```text
“什么都能回答”
```

而是：

```text
听得懂
接得住
记得住
看得出情绪
知道用户真正需要什么
知道下一步怎样做更合适
知道什么时候可以主动
更知道什么时候不能乱做
```

从工程角度可以进一步归纳为：

```text
懂人
=
语义理解
+
上下文
+
情绪
+
隐含需求

持续懂人
=
关系连续性

会陪
=
对话策略
+
主动性

不乱来
=
自我约束
```

最终：

```text
智能陪护 Agent
=
懂人
+
持续懂人
+
会陪
+
不乱来
```

这四个结果共同构成整个系统智能能力的最终评价标准。
