## 1. 产品目标、边界与成功定义

产品是一套**可运行、可复用、可扩展、可切换业务专项的 General Agent System**，不是单独的 Agent Runtime 库。通过加载完整 Domain Package，将相同业务中立的核心用于两个以上不同领域，不修改 Agent Core 实现；涉及具体领域的新工具、规则、知识和状态模型由领域包承担。

### 1.1 产品必须证明的核心能力

1. 接收并持续追踪用户目标，可选择确定性工作流或模型辅助决策模式。
2. 一个任务中能够 Observe → Reason/Plan → Act → Validate/Observe → Continue/Replan/Finish；支持模型决策但不把执行授权交给模型。
3. 从已注册、合法的候选 Tool/Skill/Workflow 中选择，经已有审批链批准后执行。
4. 知识查询、短期上下文、长期记忆、执行观察分别有明确来源和时效边界。
5. 完整业务专项包含 Prompt、Knowledge、Capabilities、Rules、State/Memory Policy、Evaluation，并能版本固定、切换、隔离。
6. 失败/取消/未知副作用/缺少证据时安全退出，并提供 Trace/Eval。
7. 在开发态跑通离线无副作用 E2E，再经过独立正向授权与生产组装证据进入生产。

### 1.2 非目标

初期不同时实现复杂多 Agent 分布式系统、跨设备大规模调度、真实医疗诊断、生产自动转账/发通知等高副作用能力。多 Agent 属于后续扩展，而非 GA-01 阻塞项。

### 1.3 成功定义

至少两个不同 Domain Package，在同一 Core、同一版本 Runtime 的条件下完成真实任务流程；无 Core 源码变更；每个任务具备多轮模型决策证据、工具输入/输出、合法批准链、终止原因和业务隔离测试。正式生产成功必须附独立的授权、部署与运行证据，不以 Demo 代替。

## 2. 总体架构与职责

```text
┌─────────────────────────────────────────────────────────────┐
│ Application / Composition Root                              │
│ Web / API / CLI / Agent Selection / Auth / Session / Deploy  │
└───────────────────────────────┬─────────────────────────────┘
                                │ resolve exact Domain binding
┌───────────────────────────────▼─────────────────────────────┐
│ Domain Package Assembly (version-pinned)                    │
│ Manifest / Prompt / Knowledge / Capability / Workflow       │
│ Rule & Policy / Domain State / Memory Policy / Eval         │
└───────────────────────────────┬─────────────────────────────┘
                                │ allowed capabilities, context policies
┌───────────────────────────────▼─────────────────────────────┐
│ General Agent Core (新增协调层；不复制既有 M3/M4)              │
│ AgentRun Coordinator / Loop Budget / Observation Adapter    │
│ Continuation & Replan / Completion / Task-level Trace       │
└───────────────────────────────┬─────────────────────────────┘
                                │ call existing interfaces
┌───────────────────────────────▼─────────────────────────────┐
│ Agent Runtime / Shared Capabilities (已有主要工程资产)       │
│ M0/M1 Context | M2 Safety Policy State | M3 Understanding   │
│ M4 Planner/Approval | M5 Execution/Recovery | M6 Validation │
│ Registry / Contracts / Trace / Context Providers            │
└─────────────────────────────────────────────────────────────┘
```

此图表示**产品职责和装配依赖**，不是要求在源码中把 `runtime/understanding`、`runtime/planning` 等现有模块物理搬进 `agent_core/`。Agent Core 通过 Adapter/Protocol 编排已有 Runtime 能力，Runtime 不反向依赖具体 Domain 或 Application。

### 2.1 Application

负责用户/租户身份确认、会话和 Agent 选择、绑定 Domain 版本、用户反馈、请求调度、业务部署、外部凭据和安全环境，不将具体业务规则硬编码到 Core。真实生产 Composition Root 属 Application 所有；PC-01 仍 DEFERRED、R-G1-03 仍 OPEN。

### 2.2 Domain Package

独立版本化业务能力包。不是只有 Prompt + 知识库，也不能改变 Core Canonical Contract、Runtime 许可规则。负责提供业务型候选 Action、Strategy、Tool、Skill、Workflow、知识映射、状态扩展、模型路由/Prompt、规则、记忆策略、验收用例。使用唯一绑定指纹/快照供整个 Agent Run 读取。

### 2.3 General Agent Core

**新增长期需要维护的最小产品核心**，只承担任务级控制而不替代模块实现：
- `AgentRunCoordinator`：任务启动、迭代控制、Run ID、跨轮结果接续。
- `DecisionAdapter`：把当前 Goal、Context、可信 Observation 投影到现有 M3/M4；不得绕过 `PlanValidator` 和 `PolicyRechecker`。
- `ObservationAdapter`：从有明确来源的 M5 执行结果和授权验证结果投影下一轮可用事实；不会把 `UNKNOWN` 变成成功。
- `ContinuationPolicy`：继续/等待/重规划/完成/阻断，执行确定性预算和安全硬门槛。
- `AgentRunTrace`：Run→Iteration→Plan→Execution→Validation 的关联；复用既有 StageTrace，不能生成独立的第二套事实源。

### 2.4 Agent Runtime

**直接复用**现有主链、合同、M3 结构化理解、M4 合法候选/规划/批准、M5 执行/可靠性/恢复、M6 NoGrant、上下文和 Runtime State。Runtime 决定动作如何被安全/有依据地执行；Agent Core 决定是否需要新一轮决策，不能直接赋予 Runtime 新权限。

## 3. 核心端到端运行流程

```text
Application Input
  -> identity/session verification -> pinned DomainBinding
  -> Task Goal & Context
  -> M1 Context + M2 Safety/Policy
  -> M3 Understanding -> M4 legal candidates / strategy / ActionPlanDraft
  -> PlanValidator -> PolicyRechecker -> ApprovedActionPlan
  -> M5 execute / journal / terminal aggregation -> ExecutionResult
  -> authorized validation boundary -> ValidatedResult / NO_GRANT
  -> ObservationAdapter -> trusted observation (if granted)
  -> ContinuationPolicy:
       FINISH (verified completion)
       CONTINUE (next authorized iteration)
       REPLAN (validated evidence + preserved policy)
       WAIT (pending/user input)
       BLOCK (denied/unknown/no evidence)
  -> response authorization / approved state update
```

**重要：当前这条完整流程是目标，不是运行事实。** 现有 `RuntimeOrchestrator` 属于固定单轮 Pipeline；GA-01 的循环不能通过私自调用 `LEGACY_TEST_COMPAT` 来获得生产正向权限。

### 3.1 一轮 Loop 的具体责任

| 阶段 | 输入 | 责任组件 | 输出或约束 |
|---|---|---|---|
| Admission | 用户任务、身份、Domain request | Application + Runtime | `AgentRunContext`（候选）、绑定快照 |
| Observe/Context | 最近可信状态与记忆 | M1 ContextBuilder + Provider | `RuntimeContext`，附来源/缺失 |
| Understand | 用户目标、上下文 | M3 Understanding Engine | `UnderstandingState`；LLM 仅理解 |
| Decide/Plan | 目标、策略候选、规则 | M4 Planner + HybridStrategySelector | `ActionPlanDraft` |
| Approve | Draft、PolicyDecision | Validator + PolicyRechecker | `ApprovedActionPlan`，否则失败 |
| Act | 已批准计划与能力绑定 | M5 | `ExecutionResult`；物理副作用需真实授权 |
| Validate | Execution + plan + context | M6 授权路径 | `ValidatedResult` 或阻断 |
| Observe result | 验证事实与未知状态 | 新 ObservationAdapter | 下一轮可信观察 |
| Continue/Stop | 观察、预算、规则、停止条件 | 新 LoopCoordinator | CONTINUE/REPLAN/WAIT/FINISH/BLOCK |

### 3.2 LLM 与确定性职责分工

LLM 可提出：目标理解、策略建议、知识查询意图、候选动作、失败解释、可选 Replan；**不能**擅自批准计划、拼接任意 Tool ID、设置权限、宣布物理执行成功、补写校验事实、突破预算。所有模型输出需模式校验和 Policy/Registry 检查。

### 3.3 停止、循环与失败

确定性停止包含：可信任务完成、拒绝/安全阻断、达到最大轮数/工具数/时间或 Token 预算、用户取消、等待外部输入、连续 N 次无进展、动作重复且证据未改变、无法取得合法动作、执行结果 UNKNOWN。异常/超时不得当成功；WAIT 不得擅自提交业务状态。每次迭代应有独立 ID、起因、父计划、预算消耗、Outcome 和 trace linkage。

### 3.4 Replan 与恢复不是一回事

- **Replan**：根据新可信观察调整后续计划，必须重新走 M4 审批；现有 `runtime/planning/replan.py::ReplanEntryRequest` 只有信息边界，限制 `trigger_stage=RESULT_VALIDATE`，不代表重规划循环已存在。
- **Retry/Recovery**：M5 对同一已批准执行的可靠性处理，不能因为工具失败就隐式重新选择 Capability、创建新业务动作或覆盖旧观察。
- 新 Agent Loop 不接管 M5 内部 Step 生命周期，也不得双重调用一个 side-effect Tool。

## 4. Domain Package 详细设计

### 4.1 候选目录结构（未冻结）

```text
domains/<domain-id>/
  manifest.yaml                  # domain_id, version, min_runtime, references
  prompts/                       # layered prompts, contracts, version
  knowledge/                     # corpus / index binding / freshness policy
  capabilities/                  # actions, strategies, tools, skills, workflows
  policies/                      # domain rules; never override Core deny
  state/                         # domain schema, memory/retention policy
  model_routes/                  # allowed model configuration references
  eval/                          # gold tasks, invalid cases, isolation tests
```

这是物理组织候选；GA-02 再决定文件格式和 Loader/Assembler 接口，避免在现阶段重新冻结整套 Schema。

### 4.2 运行时装配

加载 Manifest → 校验 schema/runtime 兼容性 → 精确版本解析 → 检查必需工具的实现绑定和权限 → 编译 Prompt / Knowledge / Rule / Workflow 引用 → 建立只读 `DomainBinding` → 产生绑定指纹 → Session/Run 引用固定快照。缺少依赖、版本歧义、重复命名空间、禁止能力或越权策略一律 fail-closed。跨包不能共享可写业务状态或泄漏记忆。

**现有情况**：`DomainRegistry` 只存储 Manifest、`PromptRegistry` 只登记元数据；不具备这一完整装配能力。

## 5. Model、Prompt、RAG 与工具

M3 的 `StructuredUnderstandingModel`、M4 的 `StructuredStrategyModel` 是不同受限模型边界；可共用底层 ModelProvider 适配器，但不能直接合并授权语义。Prompt Assembly 必须固定 Runtime 基础指令、Domain 约束、任务输入、可信观察和 Tool Schema；不可信检索内容永远是数据，不能重写系统/权限策略。

RAG 应区分 `KnowledgeNeed/Query/Plan`（已有 M4 知识规划组件）与实际检索/来源验证/上下文注入（需单独证明）。对于过期知识，采用来源/时间/检索结果等元数据判断，不能把检索命中等同真理。工具只能通过 M5 Protocol/Registry/Invoker，拒绝任意模型直接执行函数。

## 6. State / Context / Memory

| 对象 | 事实所有者 | 生命周期 | 实现状态 |
|---|---|---|---|
| Runtime Control State | `RuntimeStateEngine` | 运行控制与状态转移 | 已有实现和 InMemory Store |
| Session/Task Context | Context Provider/Application | 会话/任务 | 已有契约；长期持久化需另证 |
| Domain State | Domain schema + 授权持久化适配 | 业务域内 | `DomainExtensions` 已有挂载点 |
| Agent Run State | 新 LoopCoordinator + 持久化策略 | 一个任务跨迭代 | 需要新增、不可取代 Runtime State |
| Memory | 领域记忆策略 + 公共存取接口 | 短期/长期 | `MemoryContext` + Update Interface 存在；完整存储未证明 |

所有读写至少带 tenant/identity_scope/session/domain/version 关联，分清观察与提交权限；Memory 不能仅依据相似度自动更新/废弃事实，应有时间、生效和来源策略。长期记忆不是 GA-01 首轮上线必需，接口边界要预留。

## 7. 安全、执行真值与可观测性

固定不变量：
1. `ActionPlanDraft` 不可进入 M5；只接受 `ApprovedActionPlan`。
2. `ExecutionResult` 是物理执行观察而非已确认业务真相；`ValidatedResult` 才是验证事实来源（且还要确认授权/来源有效）。
3. `DENY_ONLY_GATED` 在 M6 NoGrant 后阻断 M7/M8。GA-01 不能绕过它再声称通过验证。
4. 测试模式必须强隔离网络/副作用，不可升级为生产可用；生产 B3 授权保持独立。
5. `UNKNOWN`、`WAITING` 和取消的操作不能虚构成功；幂等键和已有 M5 Journal 一致。
6. 一个 Run 中每轮的 Plan / Execution / Validation 精确关联，禁止跨身份/业务包混淆。

Evaluation 分五层：合同单测；组件集成；Agent Loop 任务级 E2E；双 Domain 差异/隔离；真实生产权限、安全、延迟、回归。至少覆盖工具失败、空候选、模型非法输出、Denied、无进展、超预算、未知副作用、跨域污染。

## 8. 与旧 M0–M9 的迁移策略

| 旧资产 | 新架构角色 | 迁移原则 |
|---|---|---|
| M0 | Runtime 核心主链/Trace | 保留既有单轮回归，不强改 |
| M1 | Context + Input | Provider 适配，接 DomainBinding |
| M2 | Safety / Policy / State | 强制前置和每轮 recheck |
| M3 | Understanding | 复用真实 Engine，补生产级 Model Provider |
| M4 | Planning / Selection / Approval | 复用 Planner/Validator/Rechecker，加 Loop 桥接 |
| M5 | Tool/Skill/Workflow Execution | 复用 Execution/Journaling/Recovery；不重建 |
| M6 | Result Validation | 现有限定 NoGrant 必须保留；正向授权后续处理 |
| M7 | Response interfaces | 已有主链调用及契约；具体实现/授权待审计 |
| M8 | State/Memory Update interfaces | 复用合同边界；记忆服务需补 |
| M9 | Domain/Business Extension 设计 | 转为可执行 Package Loader 目标 |
| K0 | Knowledge/RAG 设计 | 接 M4 KnowledgePlan，实际 Retrieval 待证明 |

历史设计在 `可复用Agent_Runtime平台设计/` 作为实现/冻结证据保留；旧 Runtime-first 总体方案不再作为产品纲领，但冻结合同与不变量仍是兼容性约束。

## 9. 旧版四层架构的继承映射与不可丢失的分工

本 V2.1 在新版产品层面采用 Application / Domain Package Assembly / General Agent Core / Agent Runtime 四个**职责区域**；它们不是对旧 V1.0 的 L1–L4 简单改名。旧设计必须按以下表**显式承接**：

| 旧版位置 | 新版位置 | 必须继续成立的职责 |
|---|---|---|
| L1 Agent Runtime Core（M0–M8、K0、Registry、Trace、Eval） | Agent Runtime + Shared Infrastructure；由 General Agent Core 控制多次使用 | 统一主链、执行事实、安全/状态/权限、通用知识基础设施、可观测性 |
| L2 Domain Extension | Domain Package 内的 Domain Extension 部分 | 跨产品可复用的领域 Schema、Rules、Workflow、Capabilities、Domain State、Tool Adapter |
| L3 Business Package | Domain Package 内的 Business Assets/Configuration 部分 | 单一产品的业务能力目录、内容、Prompt/Knowledge 绑定、参数配置、特性开关和评测用例 |
| L4 Application | Application / Composition Root | 用户入口、身份、租户、交互、部署、实际依赖装配 |

**决议**：保留“Domain Extension ≠ Business Package”的概念边界，但初期允许它们一起作为一个版本化 Domain Package 发布；这不意味着二者可在权限、数据生命周期和升级路径上相互替代。Domain-specific Service/Workflow 只能通过预先定义的 Capability/Adapter 接入，不能嵌入第二个隐式 Runtime。

## 10. Rule / Policy / Workflow / Capability 插件机制（继承旧版 §8–10、§13、§16）

### 10.1 Rule/Policy

旧版提出候选优先级：`Safety > Domain Hard Policy > Runtime State Constraint > Planner Preference`。这是一条**V1.0 设计原则**，不应未经核对就作为已经实现的 M2 判定顺序。GA-02/04 的设计核对必须以 `runtime/policy_management/`、`runtime/constraint_management/`、`runtime/priority_management/`、`runtime/safety/` 的真实代码和冻结不变量为准，确认冲突处置、deny 覆盖权和 forced-action 可行性。

接口层的必要信息包括 `rule_id`、`version`、`priority`、`scope`、`condition/trigger`、`effect`、`enabled`；**不是要求立即给现有 `PolicyDefinition` 增字段**。当前 `runtime/registries/definitions.py::PolicyDefinition` 记录 `rule_id/version/priority/scope/trigger/effect/enabled`，运行求值与优先级仍由现有 Engine 负责。Domain Package 配规则实例，不得授予自身绕开 Core deny 的权限。

### 10.2 Workflow

同时支持无需强业务流程的 Agent 与具有领域工作流的 Agent：
- **无强 Workflow**：模型/Planner 在合法 Action 集合中选择，使用 Agent Loop 根据 Observation 继续。
- **有 Domain Workflow**：Workflow 负责业务节点与确定性条件，Agent 可以触发已注册 Workflow、提供合法参数、在授权边界外做下一轮决策；Workflow 实例状态、checkpoint、resume 由既有 M5 权威持有。
- `WorkflowImplementation.start/resume` 是当前执行接口，不能等同于“Agent Loop 已存在”；一个 Workflow 完成也不必代表整个 Agent Goal 已完成。

Workflow 的 trigger/exit/branch/side effect 必须能够映射到明确的 Rule、Tool/Skill、Goal completion evidence。不得让 Workflow 内的隐式 LLM 重新授权外部 Tool，也不得让 Loop 管理第二套 Workflow 实例状态。

### 10.3 Capability、Skill、Tool 与 Adapter

```text
用户 Goal
   ↓
M4 Strategy / registered Action
   ↓
Capability Contract（稳定语义与输入输出约束）
   ↓
ApprovedActionPlan（授权的具体步骤与版本）
   ↓
M5 Resolver → Skill / Workflow / Tool implementation
   ↓
ExecutionResult → M6-validated evidence（若具合法授权）
```

旧版“Capability Contract 稳定，Implementation 可换”的原则继续成立：例如 Knowledge Retrieval 可以从 Vector RAG 换成 Hybrid/GraphRAG，只要能力的输入、输出、错误和证据质量仍满足已声明合同，不需要改 Agent Core。但实现更换**必须先验证**版本 pinning、权限、重试幂等语义、结果 Schema 和已有 Eval；不能因为名字相同就默许不兼容版本。

- **Capability**：对规划暴露的稳定语义能力；可有多个实现，但同一次 Run 版本必须可归因。
- **Action/Strategy**：模型可在合法集合内提出动作与策略，不能自行构造高权限能力。
- **Skill**：可复用操作封装；调用 Tool 时受已有 Invoker 授权约束。
- **Workflow**：管理业务步骤及恢复/顺序，不替代 Agent 的跨任务决策。
- **Tool Adapter**：具体外部 API/数据库/设备协议实现，只能通过既有 M5 Invoker/Journaling 进入。
- **M5 Runtime**：唯一管理物理尝试、超时、取消、重试、幂等、资源锁、事实收集的权限边界；新层不得重做。

### 10.4 技术升级的归属判定

新增能力先分类：A Runtime 共性机制、B Domain Extension、C 已有 Capability 的 Implementation、D Prompt/Knowledge/配置。**默认先检验 C 或 D 是否足够**，只有证明缺失通用机制才升级 A；不能因某个领域特例就更改主链。对每个升级记录受影响的 Contract、版本、适配器、Domain 和 E2E Case。

## 11. Prompt、Model 与 K0 知识基础设施（继承旧版 §11–12）

### 11.1 Prompt 分层

旧版保留的四层要求：

```text
Runtime Base Prompt
+ Domain Prompt
+ Task Prompt
+ Runtime Constraints
```

新版在此基础上增加**可信 Observation Context**、业务包版本、模型输出结构化约束。四层并不意味着运行时对模型输出任意信任；Safety/Policy 是非 Prompt 的确定性执行门禁。现有 `PromptRegistry` 只负责元数据登记，GA-02 的 Prompt Assembly 需实现版本解析、加载/拼接、冲突检查、渲染、审计指纹以及不可信检索内容隔离，且不得修改 `StructuredUnderstandingModel` 和 `StructuredStrategyModel` 的权限边界。

### 11.2 K0 的完整责任

**旧版 K0 设计不应因 GA-01 不需要生产 RAG 而在总架构中消失**：

```text
Knowledge Source / Source Policy / Taxonomy / Metadata
    ↓
Ingestion → Parser → Chunking → Index/Version
    ↓
Retriever → Rerank/Filter → Evidence Pack
    ↓
Evidence Validation / Freshness / Validity / Citation
    ↓
M4 KnowledgePlan / Agent Context / Claim Constraints
```

| K0 公共责任 | Domain 特有责任 | 新路线处理 |
|---|---|---|
| 文档导入、解析、切块与索引 Adapter | 知识源、分类法、访问范围、分块策略参数 | 作为公共接口设计，复用已有能力后再补缺口 |
| 检索、融合/Rerank、Evidence Pack 标准 | Domain 知识库、查询目标、证据阈值 | M4 的 KnowledgeNeed/QueryPlan 与真实检索服务分开 |
| 版本、时效、来源、授权过滤 | 医疗/教育具体更新周期、敏感等级 | GA-02 加入版本绑定，GA-05 扩展治理 |
| Trace/Eval：召回、证据质量、引用有效性 | 领域问答正确性/红旗规则 | GA-03 至少有知识替换隔离 E2E |

**现状界限**：`runtime/planning/knowledge_planning.py` 已有规划组件；它不证明完整 K0 索引、检索、重排和生产 Evidence Service 全部已实现。K0 的旧版详细设计保留作候选规范；需要在 GA-02/05 前做独立 Gap Mapping，不直接宣布 K0 READY。

## 12. Canonical Contract、Domain Schema、Identity 与 State 边界（继承旧版 §6–7）

### 12.1 主链 Canonical 合同

以当前 `runtime/contracts/`、Canonical Registry 与测试为实现权威，旧设计文本有冲突则须显式提出 Amendment，不能静默覆盖。

| 位置 | 已有/冻结合同 | 使用约束 |
|---|---|---|
| 请求与安全 | `RuntimeInput`、`SafetyResult` | Early/Deep Safety 保留阶段区分 |
| 上下文与理解 | `RuntimeContext`、`UnderstandingState`、`PolicyDecision` | Domain 数据只经 extension 或受控 payload |
| 规划与授权 | `ActionPlanDraft`、`ApprovedActionPlan` | 不恢复歧义 `ActionPlan`；M5 只接 Approved |
| 执行与真值 | `ExecutionResult`、`ValidatedResult` | Raw Observation 不冒充业务真值 |
| 响应与提交 | `ResponsePlan`、`RuntimeResponse`、`UpdateResult` | `StateUpdate/MemoryUpdate` 内部结果，不做主链终点 |

禁止 Domain Schema 通过自定义 Runtime/ToolResult 偷渡第二套执行权威。Schema Registry 应明确 Core Schema、Domain Schema 命名空间和版本兼容性；领域对象（如 DomainEntity、DomainFinding、DomainTask、DomainEvidence）是可选领域 Schema 示例，不可硬编码进 Core。

### 12.2 身份与状态

- Core 身份只能采用通用 `subject_id` 与 `identity_scope` 等既有通用合同；旧 `elder_id`、`patient_id` 等只能进入 DomainIdentity 扩展，禁止重新污染 Core。
- `RuntimeState` 管理控制态、当前工作流/任务引用、交互和等待/中断控制；`DomainState` 表示业务具体阶段，经 `RuntimeContext.domain_extensions` 挂载。
- `AgentRunState` 是新层记录 Loop 迭代/预算/目标的任务级证据，**不新建与 `RuntimeStateEngine` 冲突的状态机权威**。
- SessionContext / TaskContext / MemoryContext 是不同用途；Memory 写入、删除、纠错、生效与过期都必须遵守身份/Domain 作用域和授权更新机制。

原版 `RuntimeControlState` 枚举、各状态转移、`DomainState` 具体类型必须以当前代码及冻结合同为准，不以此总体设计写死新枚举或立即要求迁移。

## 13. Evaluation、Trace 与新业务 Agent 创建流程（继承旧版 §14–15、§18）

### 13.1 双层 Evaluation

**Core Eval**：M3 Understanding、M4 Planning、M5 Execution、M6 Validation、Response、Memory、Agent Loop、E2E/安全回归；公共系统指标包括非法工具调用率、未验证成功声明、重复副作用、预算终止、任务成功率等。

**Domain Eval**：业务 Rule Cases、Workflow Cases、Capability Cases、Safety Cases、Domain Truth/Knowledge Cases、Domain 隔离与 E2E。Domain 包必须随附本领域数据和判定规则，不能只使用 Core 单测声称业务可用。

Trace 采用 Run ID → Iteration ID → Request/Plan ID → Execution/Validation ID 的父子可追溯关系；复用原 StageTrace，并跟踪模型输入摘要、Prompt/Domain/Tool 版本、Permission、预算和停止原因（敏感数据注意脱敏）。

### 13.2 将来使用平台创建一个新 Agent 的流程

以下是**业务项目接入流程**，与 GA-00～GA-06 的**平台建设流程**相互独立，不能把后者作为前者的替代：

1. 定义新 Agent 的用户目标、成功条件、业务风险与边界。
2. 选择/创建 Domain Package、固定 Domain ID/版本与依赖。
3. 定义 Domain Schema / Domain State 和身份字段映射。
4. 注册领域 Intent、Goal/Need、Strategy、Actions 和 Rule/Policy。
5. 如有确定性业务流程，注册 Workflow 和其状态/出口条件。
6. 注册 Capability、Skill、Tool Implementation 以及输入/输出/副作用级别和权限。
7. 绑定 Prompt 层、Model Route、K0 Knowledge Source / Index / Evidence Policy。
8. 声明上下文选择、任务跨轮与 Memory 生命周期策略。
9. 附上 Eval Dataset：成功、失败、拒绝、跨身份、跨 Domain、知识时效和安全例子。
10. 运行 Manifest/Contract/Registry 兼容检查，生成不可变 DomainBinding。
11. 先跑一个无真实副作用 Vertical Slice，确认 Agent Loop 完成真实任务，再做领域 E2E。
12. 对真实外部动作另做 Permission、安全/用户确认/生产授权与部署验收。

只有一个 Domain 成功不能证明“通用”；至少第二个明显不同的 Domain 不改 Core 运行成功，才可主张 Domain 复用目标得到验证。

## 14. 禁止模式、兼容性与关键不变量（继承旧版 §17、§19）

继续禁止旧版列明的以下模式：

- 每个项目复制 Runtime；每个 Skill 单独建设不互通的 RAG/状态权威。
- 业务 Intent/Need/Action 等枚举进入 Core，Domain State 任意写入 RuntimeState。
- Prompt 分散硬编码且没有版本；知识内容或模型输出覆盖系统/权限策略。
- ToolResult 或 LLM 自述直接变为已验证业务真相。
- Capability 内隐藏第二套 Runtime；LLM 绕过 Policy 直接调用外部系统。
- 计划未批准而进入 M5；未获正向授权却宣称生产副作用成功。
- 不受预算限制的 Agent Loop、自主循环调用外部工具、无幂等恢复依据的重新执行。
- 以历史 Closure 或 Fake E2E 替代真实双 Domain 验收。

在旧版“Runtime 稳定、Domain 插件化、Capability 合同稳定、实施可替换、配置版本化、Schema 受控、评测随包交付”七条最终原则之上增加：**Agent Core 必须面向可信 Observation 组织动态任务闭环，但不得拥有 Runtime 已冻结的物理执行、授权、状态提交权威**。

## 15. 未决项和版本边界

- **D-01**：外层 Loop 如何重用现有单轮 Orchestrator 而不重复执行阶段、提前提交 Response/Update？GA-01 设计必须给出精确 Call Graph；优先 Adapter，不建议直接反复调用完整 `run()`。
- **D-02**：GA-01 “隔离测试验证结果”不能使用 M6 NoGrant 伪造生产验证 Grant；需定义只在隔离运行的 Evidence/Observation Stub 和不可达生产绑定。
- **D-03**：DomainBinding 的唯一版本指纹、依赖/存储作用域和解绑生命周期。
- **D-04**：Context/Mem 更新应在迭代还是任务完成时发生、失败时如何保持一致。
- **D-05**：Loop Run State 与 M5 Recovery 的持久化边界/重复执行防护。
- **D-06**：真实模型的结构化输出契约、成本预算、失败降级。
- **D-07**：生产 B3、Composition Root、M6 权威验证者的授权与证明。
- **D-08**：取消时 StageTraceEvent 可能残留 STARTED（原有待办）。

**冻结门槛**：以上 D-01/D-02 中涉及 GA-01 的设计和负向测试方案须收口；其余在相应 Unit 开发之前决策。总体方向可作为路线依据，不等于 GA-01 代码实现已获无条件授权。
